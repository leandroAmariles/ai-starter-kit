# HTTP test requests after implementation

Applies at the end of every implementation run: `/speckit-implement`, `/opsx-apply` (OpenSpec's
`openspec-apply-change`), or any request to "implement the tasks" of a spec. Those skills are
generated by their own CLIs, so this rule is what adds the step to them.

## When

Once the tasks are done (all checked, or the run ends with the endpoints in place) and **only if the
implementation added or changed an HTTP endpoint**. If it did not (batch job, listener, library
code), skip silently and say so in one line.

## What to generate

A single file `requests.http` (IntelliJ HTTP Client / VS Code REST Client syntax) inside the
**spec folder being worked on**:

- spec-kit: `specs/<slug>/requests.http` (the directory in `.specify/feature.json`)
- OpenSpec: `openspec/changes/<change-name>/requests.http`

Never at the repo root and never in `src/`. If the file exists, update it in place: keep requests the
user added by hand, replace the ones this run generated.

## Content

These are **test cases that validate the business logic of the spec being implemented** — not a
generic API smoke test. Read `spec.md` (spec-kit) or the change's `specs/**/spec.md` (OpenSpec) and
build the cases from it; use the code only to get the real paths, DTO fields and `ErrorCode`s:

1. **One case per requirement and per acceptance scenario** (Given/When/Then). Set up the *Given* with
   the request data, send the *When*, and state the *Then* as the expected status/body.
2. **Rule boundaries**: for every business rule, rule or limit the spec states (thresholds, states,
   conditions, calculations), a case just inside and a case just outside it.
3. **Edge cases and failure paths listed in the spec** (the "Edge Cases" section, rejected inputs,
   conflicting states), each with the error the spec expects.
4. **Sequences** when the logic depends on state (create → update → conflict): order the requests so
   they run top to bottom, capturing ids from earlier responses.

Do not add generic cases the spec does not describe (missing-field matrices, auth failures, etc.).
Include them only when a requirement says so.

Every request is traced to its source and states the expected result:

```http
### FR-003 / Scenario "Invoice over limit is rejected" — expects 422 INVOICE_LIMIT_EXCEEDED
POST {{baseUrl}}/<path>
Content-Type: application/json
Authorization: Bearer {{token}}

{ ... }
```

If a requirement has no case (it is not reachable over HTTP), list it in a comment block at the top
of the file as "Not covered here".

- Use variables (`{{baseUrl}}`, `{{token}}`, ids) declared at the top of the file; default
  `baseUrl` to `http://localhost:<server.port from the app's config>`. Never hardcode secrets or real
  customer data — use obvious placeholders.
- Group with `###` separators, one per request; add `> {% client.test(...) %}` assertions on status
  only when the response shape is certain.

## Report

End the implementation summary with the path of the generated file and the number of requests.

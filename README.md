# AI Workspace Starter Kit

A portable, multi-agent AI configuration package for software projects. Write your team's
architecture patterns, coding rules, and workflows **once**, in one agent-neutral format, and
generate the native configuration files for **GitHub Copilot, Claude, Cursor, Windsurf, and
JetBrains AI** with a single script.

Works for a personal project or an entire company: drop one small bootstrap script into your repo
(see "Installation" below), run it, and every supported AI agent starts a session already knowing
your architecture, conventions, and workflows. Re-running that same script later pulls whatever
changed in this kit since — see "Versioning & updates".

## Why this exists

Most teams end up writing the same "here's our architecture / here's our commit format / here's
our testing style" instructions over and over — once per AI tool, in that tool's own format and
location (`copilot-instructions.md`, `CLAUDE.md`, `.cursorrules`, `.windsurfrules`,
`.aiassistant/rules/`...). They drift out of sync the moment someone updates one and forgets the
others.

This kit keeps a **single canonical source** (`.ai/`) and an installer script that
generates/refreshes every agent's native files from it.

```
    │       ├── reactive-programming.md

    │       ├── domain-modeling.md
    │       ├── observability.md
    │       └── error-translation.md
    ├── rules/                  ← non-negotiable team rules (naming, commits, exceptions...)
    │   ├── development-guidelines.md

    │   ├── openspec-{propose,apply-change,update-change,explore,sync-specs,archive-change}/

```

**Context-skills vs. callable skills** — the two skill types are not the same thing:
- **Context-skills** (`.ai/context/skills/`) are read automatically, every session — they're passive
  knowledge (e.g. "this is how we structure hexagonal architecture").
- **Callable skills** (`.ai/skills/`) are explicit workflows the agent runs on request, either via
  natural language, the skill's own name (e.g. `openspec-propose`, for agents with native skill
  discovery), or its mirrored `/opsx-propose`-style command from `.ai/prompts/` (see the table below
  for which agents receive which).

## Installation

### The simplest way: a bootstrap script in the consuming repo (recommended)

For a microservice repo, don't vendor this kit at all — the repo only ever needs one small file,
[`ai-bootstrap.sh`](./ai-bootstrap.sh) (checked into this repo, ~30 lines). Every time it runs, it
clones this repo fresh and decides what to do on its own: `--init` (first-install wizard) if the
target repo has no `.ai/` yet, or `--update` (see "Versioning & updates" below) if it does.

**Get the file into a target repo once** — this repo is public, so a plain `curl` of the raw file
works with no token or auth needed:

```bash
curl -fsSL https://raw.githubusercontent.com/leandroAmariles/ai-starter-kit/main/ai-bootstrap.sh \
  -o ai-bootstrap.sh
```

(If you already have `gh` or `git` set up, `gh api repos/leandroAmariles/ai-starter-kit/contents/ai-bootstrap.sh --jq '.content' | base64 -d > ai-bootstrap.sh`
or a plain `git clone --depth 1` + `cp` work too — no credentials required for either now.)

Then, in the target repo:

```bash
chmod +x ai-bootstrap.sh
git add ai-bootstrap.sh   # commit it — the only kit-related file this repo needs to keep
./ai-bootstrap.sh
```

Running it:

- **Not installed yet:** clones this repo and runs the interactive wizard (`--init`) — same
  experience as running the installer by hand, just without needing a local checkout first.
- **Already installed, any version:** clones this repo and runs `--update` (see "Versioning &
  updates" below) — adds what's new, refreshes what you never customized, leaves your
  customizations alone with a `*.new` sibling to merge by hand, regenerates the native agent files,
  and validates the result. Safe to re-run any time, including when already current (it just
  reports "up to date" and exits clean).

Set `AI_KIT_REF` (e.g. `AI_KIT_REF=v1.0.0 ./ai-bootstrap.sh`) to pin a specific tag instead of
always tracking `main`.

### The manual way: clone this repo yourself

Prefer a local checkout over the bootstrap script (e.g. to run `--copy`, `--scan`, `--agents`, etc.
individually, or to hack on the kit itself)? Clone this repo and run `install-ai-package.sh`
directly against your target repo — everything below assumes that setup.

### Checklist for applying this kit to a (new) project

Follow this in order every time you install the kit into a repo — most steps are one command, but
two of them can't be automated and are easy to forget, which is exactly when this kit's promise
("every agent already knows your architecture") quietly stops being true.

| # | Step | Why |
|---|---|---|
| 1 | Have a local copy of `ai-starter-kit/` reachable (this repo, or your own fork/clone of it) | The installer only ever reads from its own `.ai/`/`graph-rag/` source — it never invents content, so the kit itself has to exist somewhere on disk first. |
| 2 | Run `./install-ai-package.sh --init <path-to-target-repo>` | One prompt-driven pass instead of remembering the 5-7 manual commands below and their required order. |
| 3 | Answer **which agent(s)** | Generating native files for a tool nobody on the team uses is pure clutter, and it's one more place instructions can drift out of sync later. |
| 4 | Answer **which spec-driven workflow** (OpenSpec / spec-kit / none) | Picking one avoids ending up with two overlapping slash-command sets (`/opsx-*` and `/speckit-*`) for the same idea. Skip both if your team doesn't do spec-driven planning at all. |
| 5 | Answer **install the Neo4j graph?** | It's optional because it costs Docker + a few hundred MB of Python ML dependencies (`torch`, `transformers`, `sentence-transformers`) and several minutes the first time — only say yes if you'll actually use it to query architecture instead of grepping. |
| 6 | *(only if you chose spec-kit in step 4 **and** yes in step 5)* Nothing to do — the installer auto-appends an "Architecture graph" section to `speckit-plan`/`speckit-tasks`/`speckit-implement` | Without this hook, the graph is fully working but nobody — human or agent — is ever reminded it exists at the moment it would actually save tokens: while planning/implementing a spec. (OpenSpec isn't hooked yet — see "Choosing a spec-driven workflow" if you want to add it there too.) |
| 7 | **(Manual, needs an LLM)** If you installed the graph, ask your AI agent: *"Read and execute `graph-rag/pipeline_tasks.md`"*, then run `graph-rag/.venv/bin/python ingestion/phase2_embed_ingest.py` (`.venv\Scripts\python.exe` on Windows) | Phase 1 (structural scan) is deterministic and scripted; Phase 2 (one summary per class, used for semantic search) requires judgment about what a class *does*, which only an LLM can produce — the bash installer deliberately doesn't fake this. |
| 8 | **(Manual, one-time per session)** Restart your AI agent / editor session after Step 5 finishes | The installer writes a `graph-rag` MCP server into `.mcp.json` automatically, but MCP servers are only loaded when a session starts — the agent you're mid-conversation with right now cannot pick up a server that didn't exist yet. |
| 9 | Run `./install-ai-package.sh --check <path-to-target-repo>` | Single command that tells you exactly what (if anything) from steps 3-8 is still incomplete, instead of you re-reading this whole README to check. |
| 10 | *(Optional sanity check)* `graph-rag/.venv/bin/python queries/graph_rag_query.py "<a real question about this repo's domain>"` | Confirms the semantic search actually returns sensible, project-specific results before you rely on it during real spec work — a green `--check` only proves the pieces exist, not that retrieval quality is good. |

### The easy way: interactive wizard

```bash
./install-ai-package.sh --init /path/to/your-repo
```

Prompts for which agent(s) you use, which spec-driven workflow you want (OpenSpec / spec-kit /
none), and whether to install the optional Neo4j graph — then runs every step below for you.

### Step 1 — the AI configuration (required), the scriptable way

```bash
# 1. Install the canonical .ai/ folder into your target repo
./install-ai-package.sh --copy /path/to/your-repo

# 2. Choose a spec-driven workflow (openspec is the default if you skip this step)
./install-ai-package.sh --workflow speckit /path/to/your-repo   # or: openspec | none

# 3. Scan the target repo to generate its project-specific context
./install-ai-package.sh --scan /path/to/your-repo

# 4. Generate native files for the agent(s) you use
./install-ai-package.sh --agents copilot,claude,cursor,windsurf,jetbrains /path/to/your-repo

# 5. Install the chosen workflow for each agent via its official CLI (openspec or specify)
./install-ai-package.sh --openspec copilot,claude,cursor /path/to/your-repo
./install-ai-package.sh --speckit copilot,claude,cursor /path/to/your-repo

# 6. After editing .ai/ later, regenerate files for whichever agents are already installed
./install-ai-package.sh --sync /path/to/your-repo

# 7. Validate everything landed correctly
./install-ai-package.sh --check /path/to/your-repo
```

`--check` is a read-only post-install validation: confirms `.ai/` and each detected agent's main
file and skill/workflow files exist and have valid front-matter, warns if the chosen spec-driven
workflow's real CLI setup (`openspec/config.yaml`, `.specify/`) or the optional graph-rag/PR
template are missing, reports whether graph-rag Phase 1 (AST scan) and Phase 2 (summaries +
embeddings) have actually run, and flags absent prerequisites — but only for the pieces you
actually installed (git always; Docker/Python only if `graph-rag/` exists; Node/npx or uv/uvx only
if that workflow was chosen). It exits non-zero only on hard errors, like a missing or empty agent
file. Run it after every install or re-install — it's the fastest way to know what, if anything,
still needs a manual step.

`--scan` currently detects Maven (`pom.xml`), npm (`package.json`), Gradle
(`build.gradle`/`build.gradle.kts`), and Go (`go.mod`) projects, and writes a
`.ai/context/project-context.md` snapshot (stack, modules, key dependencies, CI/CD files).

### Choosing a spec-driven workflow: OpenSpec vs. spec-kit vs. none

Both are alternatives for the same idea (turn feature work into planning artifacts before code) —
pick one, or neither:

| | OpenSpec | spec-kit |
|---|---|---|
| What ships in this kit as a default/fallback | Static `.ai/skills/openspec-*` + `.ai/prompts/opsx-*`, a frozen snapshot of the `openspec` CLI's own generated output | Nothing static — always delegated to the official CLI |
| What actually makes it work | Run `--openspec <agents> <repo>` — this runs the real `openspec init --tools <slug> --force` CLI (via `npx` if not installed), which creates **`openspec/config.yaml` + `changes/`** (the static skill files alone have nothing to act on without this) and overwrites the frozen snapshot with your installed CLI's current version | Run `--speckit <agents> <repo>` — runs `specify init --here --force --non-interactive --integration <slug>` (via `uv`/`uvx` if not installed) |
| Workflow | propose → apply → archive | constitution → specify → clarify → plan → tasks → analyze → implement |
| Where its files land | Wherever `openspec init --tools <slug>` puts them per agent (confirmed against CLI 1.13.0: `.claude/skills/openspec-*` + `.claude/commands/opsx/*`, `.cursor/skills/openspec-*` + `.cursor/commands/opsx/*`, and — for windsurf — `.devin/skills/openspec-*` + `.devin/workflows/opsx-*`, **not** under `.windsurf/`; see the note below the next table) — until you run `--openspec`, only the static snapshot from `.ai/skills/openspec-*`/`.ai/prompts/opsx-*` is present | Wherever `specify init --integration <agent>` puts them (confirmed: `.github/skills/speckit-*` for Copilot, `.claude/skills/speckit-*` for Claude) |

Picking `speckit` or `none` with `--workflow` **removes** `.ai/skills/openspec-*` and
`.ai/prompts/opsx-*` from the destination's `.ai/` before generation, so they never reach any
agent. Run `--workflow` before `--agents`/`--sync` for the choice to take effect (or re-run
`--sync` afterward). Picking `openspec` (the default) keeps them as a working-but-frozen fallback
until you also run `--openspec`, at which point the real CLI takes over.

Both `--openspec <agents> <repo>` and `--speckit <agents> <repo>` were tested against the real,
current CLIs. Neither tool's `--tools`/`--integration` slugs match this kit's own agent names or
each other's, and the installer maps what it could confirm by actually running each CLI:

| This kit's agent name | OpenSpec `--tools` value | spec-kit `--integration` value |
|---|---|---|
| `copilot` | `github-copilot` | `copilot` |
| `claude` | `claude` | `claude` |
| `cursor` | `cursor` | `cursor-agent` |
| `windsurf` | `devin` | *(not currently listed as a spec-kit integration)* |
| `jetbrains` | *(no confirmed slug — a `junie` value exists in OpenSpec's list, unclear if it's the same product as "JetBrains AI Assistant")* | *(same uncertainty)* |

**About `windsurf` → `devin`:** as of OpenSpec CLI 1.13.0, `openspec init --help` lists `devin` as
the real `--tools` value and says `windsurf` is "now devin" — an accepted-but-deprecated alias, kept
for backward compatibility only. Running it (either value; confirmed identical output) sets up an
integration the CLI itself labels **"Devin Desktop (formerly Windsurf)"** and writes it entirely
under **`.devin/`** — `.devin/skills/openspec-*/SKILL.md` and `.devin/workflows/opsx-*.md` — not
`.windsurf/`. This kit uses the non-deprecated `devin` value so it keeps working if a future OpenSpec
release drops the alias. This rename is scoped to OpenSpec's own generated output: this kit's own,
separate Windsurf conventions (`.windsurfrules`, `.windsurf/rules/*`,
`.windsurf/workflows/commit-and-push.md` / `neo4j-architecture-graph.md`, and the static
`.windsurf/workflows/openspec-*` snapshot before `--openspec` has run) are unaffected and still land
under `.windsurf/` as before — whether the underlying editor itself has also renamed those
conventions is unconfirmed, so this kit does not guess and leaves them as-is. `--openspec windsurf
<repo>` removes the now-stale static `.windsurf/workflows/openspec-*.md` files once the real `.devin/`
integration is in place; `--check` flags it if an older install still has both.

`--speckit`/`--workflow speckit` also runs `specify extension add git` once per repo (after the
per-agent `init` calls). Without it, `/speckit-specify` never creates a feature branch: current
spec-kit versions moved branch creation out of the core command and into an optional
`before_specify` hook (`.specify/extensions.yml`), which only this official "git" extension
registers — a plain `specify init` does not set it up on its own. Safe to re-run (detects an
already-installed extension and no-ops); if it fails for some other reason, the warning gives you
the exact command to run by hand from the repo.

For the two unconfirmed cases, the installer prints a warning instead of guessing wrong — run
`openspec init --help` or `specify integration list` from your repo to check current options.

### Step 2 — the Neo4j architecture graph (optional)

`graph-rag/` is **not** installed by Steps 1/3/4 above — it's a separate, opt-in step for when you
want a local, queryable graph of your codebase (and optionally of several microservices at once).
Run it whenever you're ready:

```bash
./install-ai-package.sh --graph /path/to/your-repo
```

This copies `graph-rag/` into the target repo, then bootstraps it: creates `graph-rag/.venv` and
installs its Python dependencies, starts a local Neo4j container (`docker compose`), runs the
deterministic Phase 1 scan (AST-parses Java into `Class` nodes, everything else into `Document`
nodes), and writes a `graph-rag` MCP server entry into the target repo's `.mcp.json` (see "Querying
the graph" below). Prerequisites: Docker + Docker Compose, and either `uv`/`uvx` or Python 3.11+.
Each of these steps prints a warning and skips gracefully — without failing — if a prerequisite is
missing; the warning includes the exact command to finish setup manually once you have it.

If `uv` is available, the venv is pinned to Python 3.12 instead of whatever `python3`/`python`
resolves to on `PATH`. Reason: one of the embedding pipeline's dependencies
(`tree-sitter-languages==1.10.2`) ships no prebuilt wheel for very new CPython releases (confirmed
missing on 3.14) — pinning avoids a dependency-install failure on an otherwise fully supported
"3.11+" machine. `uv` also creates the venv without `pip` bundled, so dependency installation goes
through `uv pip install` in that case instead of the venv's own `pip`.

### Querying the graph

Two ways to actually use what Phase 1/2 built, both read-only:

1. **MCP (recommended once configured):** the `graph-rag` entry `--graph` wrote into `.mcp.json`
   runs the official `mcp-neo4j-cypher` server (via `uvx`, read-only, namespaced `graph-rag` so its
   tools show up as `mcp__graph-rag__graph-rag-get_neo4j_schema` /
   `mcp__graph-rag__graph-rag-read_neo4j_cypher` — the namespace keeps them identifiable even if you
   also have another Neo4j MCP server configured elsewhere pointed at a different database).
   **Restart your AI agent session** after `--graph` finishes — MCP servers are only loaded at
   session start, so the agent you're already talking to won't see it until then.
2. **CLI fallback, and the only way to get semantic (vector) search:**
   ```bash
   graph-rag/.venv/bin/python queries/graph_rag_query.py "Which adapters implement the orders port?"
   ```
   Embeds the question with the same model used in Phase 2, runs a vector search over the `Class`/
   `Document` summaries, and expands one hop of `IMPLEMENTS`/`DEPENDS_ON`/`EXTENDS` for context. Use
   `--json` for machine-readable output, `--top N` to change how many results come back, and
   `--project <name>` to scope to one repo once more than one is ingested (see below).

**Feeding more than one project into the same graph:** edit `graph-rag/.env`'s `PROJECT_PATHS` to
a comma-separated list of local repo paths (e.g.
`PROJECT_PATHS=orders=.,payments=../payments-service`) and re-run
`graph-rag/.venv/bin/python ingestion/phase1_scan.py`. Every project gets its own `(:Project)` node
and every `Class`/`Document` is scoped to it, so ingesting one repo never touches another's nodes.
If one project's `pom.xml` depends on a Maven coordinate another ingested project publishes, a
`DEPENDS_ON_PROJECT` edge links them — this is how the graph represents "how does this interact
with my other microservices" (see `graph-rag/README.md` for the full explanation and Cypher
examples, including how to extend it to runtime/API-call detection later).

**Growing the graph one independent microservice install at a time (no central list to maintain):**
the recipe above assumes one checkout's `PROJECT_PATHS` lists every sibling repo by path — fine for
a few services from one machine, but it means whoever adds a new microservice has to remember to
edit that one `.env` and re-run the scan. The alternative: install this kit's Step 2 independently
in *each* microservice, and have all of them write into the **same** Neo4j instead of each spinning
up its own isolated container.

1. Pick one repo (or a dedicated ops/infra repo) as the "hub" and run `--graph` there as normal —
   this is the one that actually owns the running Neo4j container.
2. In every other microservice, install the kit and run `--graph` too, but before its first
   `phase1_scan.py`, point that repo's own `graph-rag/.env`'s `NEO4J_URI` at the hub's Neo4j instead
   of its own (`bolt://<hub-host>:7687` — `localhost` if it's the same machine). Leave that repo's
   own `PROJECT_PATHS` at the default `.` (just itself).
3. Each repo now runs its own `graph-rag/.venv/bin/python ingestion/phase1_scan.py` independently,
   whenever it wants to refresh — since every write is scoped to `(project, group)` (see
   `reconcile_inventory` in `graph-rag/ingestion/graph_ingestor.py`), one project's scan can never
   see or touch another project's nodes. The graph only ever grows; nothing already ingested is lost
   by a sibling repo's own scan.

Two relationship kinds connect across projects **for free**, incrementally, with no combined scan
ever required: Kafka `:Topic` nodes and `:Database` nodes are keyed by name (+ `PROJECT_GROUP`), not
by project, so if two independently-scanned services produce/consume the same topic or resolve to
the same datasource, their classes/projects both point at the same shared node the moment each one
is ingested — the messaging or data coupling becomes visible in the graph without any extra step.
The one limitation: the three *explicit* cross-project edges — `DEPENDS_ON_PROJECT` (shared Maven
coordinates), `CALLS_SERVICE` (a verified `@FeignClient`/WebClient/RestTemplate target — see below),
and the convenience `SHARES_DATABASE` edge — are only computed among the projects listed in one
single `phase1_scan.py` invocation's `PROJECT_PATHS`, so a purely decentralized per-repo scan won't
compute new ones of those three against siblings it didn't list; run an occasional combined scan
from any one checkout (its `PROJECT_PATHS` listing every sibling's local path, same recipe as above)
if you want those specific edges kept current too.

**Detecting outbound REST calls:** besides `@FeignClient(name="X")`, a class is also linked with
`CALLS_SERVICE` when it builds a `WebClient`/`RestTemplate` off a literal base URL — either a
hardcoded `.baseUrl("http://host:port")` or a `@Value("${some.prop:http://host:port}")` default —
and that URL's hostname becomes the target (verified against a real `:Project` node if the hostname
matches a configured project, otherwise an `:ExternalService` node, exactly like Feign). A bare
`localhost`/`127.0.0.1`/`0.0.0.0` default is deliberately skipped rather than linked, since it names
no real service (typically a local-dev fallback for infra outside the graph, e.g. a self-hosted ML
inference endpoint) — consistent with this whole pipeline's "verify, don't fabricate" rule for
relationships. A URL built from a runtime variable/method call (not a literal) is skipped for the
same reason.

To recap the two phases: **Phase 1** (the deterministic structural graph — classes, annotations,
`IMPLEMENTS`/`DEPENDS_ON` edges) is what `--graph` automates end to end. **Phase 2** (one summary
per class/document plus its embedding, what makes `graph_rag_query.py`'s semantic search possible)
needs an LLM to write those summaries, so it's the one step in this whole kit the installer
deliberately cannot do for you — see checklist step 7 above.

If you skip Step 2 entirely, the `neo4j-architecture-graph` callable skill in `.ai/skills/` simply
goes unused — it has no effect on Step 1's agent configuration.

### Where each agent's files land

| Agent | Main file | Context-skills → | Callable skills (`.ai/skills/*`) → | Receives prompt files? |
|---|---|---|---|---|
| GitHub Copilot | `.github/copilot-instructions.md` | `.github/instructions/*.instructions.md` | `.github/skills/<name>/SKILL.md` | Yes — `.github/prompts/` |
| Claude | `CLAUDE.md` | `.claude/<slug>.md` | `.claude/skills/<name>/SKILL.md` | Yes — `.claude/commands/` |
| Cursor | `.cursorrules` | `.cursor/rules/<slug>.mdc` | `.cursor/skills/<name>/SKILL.md` | Yes — `.cursor/commands/` |
| Windsurf | `.windsurfrules` | `.windsurf/rules/<slug>.md` | `.windsurf/workflows/<name>.md` | No — equivalent content already in the workflow file |
| JetBrains AI | `.aiassistant/rules/project.md` (+ `AGENTS.md` overview) | `.aiassistant/rules/<slug>.md` | Not distributed yet (no confirmed native convention) | No |

Each agent's main file is generated by concatenating `.ai/context/README.md` with every file
under `.ai/rules/`. Context-skills (`.ai/context/skills/*.md`, passive/always-loaded) and callable
skills (`.ai/skills/*/SKILL.md`, explicit workflows like OpenSpec) are distributed separately, each
into that agent's own native convention — the `.claude/skills/` and `.cursor/skills/` paths were
confirmed by inspecting what the real spec-kit `specify init` CLI writes for those agents. Nothing
in `.ai/` is agent-specific by default — see "Adding an agent-specific convention" below if you
need one agent to behave differently from the rest.

### Tracking token usage per spec (optional)

```bash
./install-ai-package.sh --statusline claude    # or: copilot
```

User-level, not project-scoped — installs `~/.claude/statusline.py` (or `~/.copilot/statusline.py`)
and wires it into that tool's `statusLine` config. It's also run automatically by `--agents`/`--init`
whenever that agent is selected, so you normally don't need to run it by hand. Two things it does:

1. **Live status line:** shows this turn's input/output tokens and running session cost while you
   work.
2. **Per-spec accumulation:** if the current git branch matches a `specs/<branch>/` directory (the
   spec-kit convention), it accumulates tokens into `specs/<branch>/.token-usage.json` — keyed by
   tool (`"claude"`, `"copilot"`) so both can write to the same file without clobbering each other —
   which the `commit-and-push` skill reads to report a real total in that spec's PR.

Each entry also gets a `cost_usd` estimate. Claude defaults to Anthropic's published per-model
pricing, looked up by the model id in the statusline payload; override it (or price Copilot, which
has no published per-token rate to default to) with:

```bash
TOKEN_PRICE_INPUT_USD_PER_MTOK=2.00    # USD per 1M input tokens
TOKEN_PRICE_OUTPUT_USD_PER_MTOK=10.00  # USD per 1M output tokens
```

Set both to override Claude's default (e.g. for partner/Bedrock pricing) or to give Copilot a rate
based on your own credit-to-dollar conversion. Coverage caveat that's also written into every entry's
`note` field: only each tool's own main thread is counted — subagent/Task-tool token usage isn't
included, since there's no verified way to capture that today. Cursor CLI has an officially
documented equivalent (with per-turn tokens) that isn't wired up yet — no confirmed usage of it in
this kit's own projects to build/test against. Windsurf's hook system and JetBrains have no
confirmed equivalent.

## Day-to-day usage

Once installed, the AI agent already knows your architecture, your commit conventions, your
error-handling model, and your testing approach — you don't need to re-explain them every
session.

You can invoke callable skills two ways:
1. **Natural language (recommended):** just ask ("let's plan a new feature", "start implementing
   the active change") — the agent is instructed to map your intent to the right skill on its own.
2. **Explicit command:** use the slash command directly (`/opsx-propose`, `/opsx-apply`, ...) where
   your agent received prompt files (see the "Where each agent's files land" table above), or the
   skill's own name (`openspec-propose`, `openspec-apply-change`, ...) for agents with native skill
   discovery.

If you chose OpenSpec (see "Choosing a spec-driven workflow" above), the callable skills implement
`explore → propose → apply → sync-specs → archive`. If you chose spec-kit instead, use its own
`/speckit-specify`, `/speckit-plan`, `/speckit-tasks`, `/speckit-implement` commands (and optional
`/speckit-constitution`, `/speckit-clarify`, `/speckit-analyze`) — spec-kit generated those for you
directly. Either way, `neo4j-architecture-graph` is also available for querying the local code
graph if you installed Step 2. See `.ai/skills/README.md` and `.ai/prompts/README.md` for details.

### Opening pull requests

`--copy` installs `.ai/templates/pull_request_template.md` as `.github/pull_request_template.md`
in your repo (GitHub's native convention — it also pre-fills the description box when you open a
PR from the web UI). The `commit-and-push` skill uses that same file: ask the agent to "commit and
push this" or "open a PR" and it stages the relevant files, writes a Conventional Commits message,
pushes, and runs `gh pr create` with the template filled in — never against the default branch,
never force-pushing, and never checking a box it didn't actually verify. See
`.ai/skills/commit-and-push/SKILL.md` for the full guardrails (and how to adapt the last step for
GitLab/Bitbucket instead of GitHub's `gh` CLI).

### Auto-enrichment

If the agent notices you consistently using a pattern that isn't documented yet (e.g. a new
testing idiom used twice), it drafts a proposal to add it to `.ai/context/skills/` and asks for
your approval before touching anything — it never edits `.ai/` silently. See
`.ai/rules/auto-enrichment.md` for the full protocol.

### Session identity canary

`.ai/rules/session-identity-canary.md` is a small, self-check mechanism against context
degradation on long sessions: at the first turn of a new session, the agent asks for your
preferred name, then prefixes every later response with `<name>:`. If that prefix ever goes
missing, changes unprompted, or looks wrong, treat it as a signal that the agent's context has
drifted (e.g. after a very long session, a compaction, or a broken tool call) and ask it to
re-confirm your name before trusting further repository changes.

It costs one extra question at the start of a session in exchange for a cheap, always-visible
signal that the instructions in `.ai/` are still being honored. Delete
`.ai/rules/session-identity-canary.md` if you don't want this behavior — like every file under
`.ai/rules/`, removing it takes effect for every agent the next time you run `--sync`.

## Versioning & updates

The kit is versioned like any other dependency: `ai-starter-kit/.ai/VERSION` holds its current
[SemVer](https://semver.org/) number, `CHANGELOG.md` documents what changed at each version, and
every installed repo can pull a newer version with one command — the same shape as bumping a Maven
`<dependency><version>`, just without a package registry in between (the "registry" is simply this
kit's own `.ai/` on disk, wherever your team keeps its clone/checkout).

**Cutting a new version** (kit maintainer, in *this* repo):
1. Edit whatever needs to change under `.ai/` (a rule, a context-skill, a new skill folder...).
2. Bump `.ai/VERSION` (SemVer: MAJOR.MINOR.PATCH — see the rule-of-thumb in `CHANGELOG.md`).
3. Add an entry to `CHANGELOG.md` describing the change.
4. Commit/tag/publish this repo however your team distributes it (a git tag, a shared clone path, a
   release archive — the installer only needs a filesystem path to `ai-starter-kit/` at update time,
   it doesn't fetch anything over the network itself).

**Pulling an update into an already-installed repo — one command, ready to use:**

```bash
./install-ai-package.sh --update <repo>
```

This replaces the repo's `.ai/` content with the current version (see the diff rules below),
automatically regenerates native files for every agent already detected there (the same thing
`--sync` does — no need to run it separately), and finishes with the same validation `--check`
does. Nothing else to run afterward, unless the report flags customized files (see below).

`--update` diffs the kit's current `.ai/` against the destination's `.ai/`, file by file, using a
per-file sha256 baseline it maintains automatically in `.ai/.ai-manifest.json` (destination-local,
never hand-edit it, and not part of what ships from the source kit):

| Situation | What `--update` does |
|---|---|
| File is new since the version the repo has installed | Adds it |
| File exists and the repo never touched it (hash still matches the last synced baseline) | Overwrites it with the new content |
| File exists and the repo **customized** it (hash no longer matches the baseline) | Leaves it alone, writes the incoming version next to it as `<file>.new` for you to merge by hand |
| File the repo removed on purpose (e.g. `--workflow speckit` pruning `.ai/skills/openspec-*`) | Never recreated |
| File the new kit version removed, and the repo's copy was still unmodified | Deleted |
| File the new kit version removed, but the repo had customized it | Left in place (orphaned — no longer tracked upstream) |

`.ai/VERSION` itself is just another tracked file, so it updates to the new version automatically
once nothing else needs manual attention. If `--update` reports customized files, resolve each
`<file>.new` (diff it against `<file>`, merge what you want, delete the `.new`) and run `--update`
again — it will keep flagging that path as customized until you do, so it never silently loses your
edits; everything else about the repo (native agent files, version) is already up to date in the
meantime. This replaces the old manual `cp` + `--sync` dance for edits to existing files; `--copy`'s
no-clobber behavior (only ever adds files that don't exist yet) still works exactly as before and is
what `--init`/first install use.

`--check <repo>` (also run automatically at the end of `--update`) reports whether the installed
version matches what's available in the source kit, so you don't need to remember to look.

## Making changes to the kit and syncing them

`ai-starter-kit/.ai/` (this repo, the canonical source) is the only thing you should edit — never a
generated file (`CLAUDE.md`, `.claude/skills/*`, `.github/copilot-instructions.md`, etc.), since the
next `--sync` overwrites it. `--sync`/`--agents` only ever read from `<repo>/.ai/`, never from this
source kit directly — that's what makes each installed repo's `.ai/` safely customizable on its own
(see "Customizing for your project" below) without a stray `--copy`/`--update` silently overwriting
someone's edits (see the table above — customized files are always left alone).

For a repo that's already installed, use `--update` (see "Versioning & updates" above) regardless of
whether your change added a new file or edited an existing one — it handles both in one pass,
regenerates the agent files, and validates the result, all in that single command, and is now the
recommended path. The old two-step manual process (`--copy` for new files, `cp` by hand for edits to
existing ones, then `--sync`/`--check`) still works if you'd rather skip the version/manifest
bookkeeping, but won't tell you which files were customized.

## Customizing for your project

- **Different stack:** the context-skills shipped here (`hexagonal-architecture`,
  `reactive-programming`, `testing-java`, `domain-modeling`, `observability`,
  `error-translation`) default to a **Java/Spring/Maven** profile. For another language or
  framework, replace or add files under `.ai/context/skills/` following the same structure:
  *What this pattern is → How to apply it → Anti-patterns to avoid*.
- **Different rules:** edit `.ai/rules/development-guidelines.md` freely — naming conventions,
  coverage thresholds, PMD/Checkstyle rules, commit format, and the exception-handling model are
  all defaults, not requirements.
- **Your own proprietary skills:** add organization-specific callable skills (e.g. a private
  internal-library catalog, or a guide for integrating with an internal system) under
  `.ai/skills/<skill-name>/SKILL.md`, following the structure documented in `.ai/skills/README.md`,
  then `--copy`/`--sync` it into each installed repo you want it in (see "Making changes to the kit
  and syncing them" above) — it reaches every agent already generated there.
- **Adding an agent-specific convention:** if one particular agent needs a convention the others
  shouldn't get (for example, a commit co-author trailer some tool requires), do not add it to
  `.ai/rules/*.md` — that file is concatenated into every agent's output. Instead, edit that
  agent's `generate_<agent>()` function in `install-ai-package.sh` to append the extra convention
  only for that agent, or append it to the generated file after installation.

## Uninstalling

The installer never deletes anything on its own. To remove the kit from a repo, delete `.ai/` and
whichever native agent files/directories you no longer want (see the table above). If you also
installed Step 2, additionally:

```bash
(cd graph-rag && docker compose --env-file .env down -v)   # stops Neo4j and deletes its data volume
rm -rf graph-rag .mcp.json
```

If you installed spec-kit, `.specify/` is spec-kit's own directory (not this kit's) — remove it
only if you don't use spec-kit outside this installation too, since a bare `specify init` may have
been run in that repo independently of this kit.
